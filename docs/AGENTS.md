# Руководство для агентов и участников проекта

Perfect World Guild Forum — сайт гильдии на Python и Django: форум, профили, приём заявок, аукцион за очки активности, ивенты, уведомления и интеграция с TeamSpeak. Развивайте существующий проект с учётом его архитектуры и оформления.

Эти правила относятся ко всему репозиторию через корневой `AGENTS.md`. Технический источник — [DEVELOPMENT.md](DEVELOPMENT.md). Изменения архитектуры и команд отражайте там, рабочие договорённости — здесь.

## 1. С чего начать

| Прочитать | Для чего |
|---|---|
| [DEVELOPMENT.md](DEVELOPMENT.md) | Стек, запуск, тесты, миграции, секреты, Docker, релизы и TeamSpeak |
| [README.md](../README.md) | Возможности проекта и способы установки |
| [GUIDE.md](GUIDE.md) | Поведение сайта для пользователя и администратора |

| Код затронутого приложения и его тесты | Определения, права доступа и бизнес-логика |

Если задача связана с issue или PR, прочитайте описание и доступные обсуждения. Перед реализацией проверьте, нет ли уже подходящего изменения. Не публикуйте комментарии от имени пользователя без его поручения.

## 2. Карта проекта

```text
app/
  config/                настройки Django и корневые URL
  core/                  настройки сайта, админ-панель и секреты
  forum/                 форум и права доступа
  profiles/              профили, регистрация и таблица активности
  reception/             заявки, обсуждения и решения
  auction/               лоты, ставки и операции с очками
  events/                ивенты, отряды и ответы на приглашения
  notifications/         уведомления сайта
  backups/               резервное копирование и Яндекс Диск
  teamspeak/             API сайта, задачи бота и учёт присутствия
  demo/                  вымышленные данные и демо-роли
  templates/             шаблоны сайта и админ-панели
  static_src/            исходники CSS, JavaScript и иконок
cli/guild.py             установка и управление сервером
tsbot/                   отдельный бот TeamSpeak
docker/                  конфигурация Caddy и запуск контейнера
docs/                    документация и скриншоты
```

Основной сайт использует Python 3.13+ и Django 6. Локально доступна SQLite, в Docker — PostgreSQL. `cli/guild.py` сохраняет совместимость с Python 3.8 и использует только стандартную библиотеку. Бот `tsbot/` также обходится стандартной библиотекой и общается с сайтом через HTTP API.

## 3. Основные правила

1. **Сначала проверка, потом вывод.** Откройте определение перед использованием. Подтвердите причину проблемы в коде, даже если в задаче указан предполагаемый файл.
2. **Изменения по задаче.** Исправляйте причину в подходящем приложении. Сохраняйте права доступа и пользовательские сценарии. Не добавляйте попутный рефакторинг и зависимости без необходимости.
3. **Одна бизнес-логика.** Используйте существующие сервисы и проверки. Шаблон, API и фоновая команда должны опираться на общие правила.
4. **Сохраняйте работу пользователя.** Не откатывайте посторонние изменения. Перед редактированием и коммитом проверяйте diff; включайте только относящиеся к задаче файлы.
5. **Проверяйте существенное поведение.** Для ошибки добавляйте регрессионный тест, когда он воспроизводит причину и защищает результат. Для оформления нужна визуальная проверка; тест HTML не заменяет браузер.
6. **Сообщайте только проверенное.** Указывайте фактически выполненные проверки и ограничения. Отдельная карточка не равна всей странице, эмуляция не равна физическому телефону.
7. **Продолжайте разрешённую работу.** Рутинные обратимые действия выполняйте самостоятельно. Уточняйте обязательные недостающие данные и действия за пределами поручения, которые трудно отменить.

## 4. Локальный запуск и демо

Для разработки и просмотра интерфейса запускайте локальный сайт командой. Пересборка Docker для каждой правки вёрстки не нужна. Контейнеры обновляйте по запросу пользователя или при проверке поведения, зависящего от контейнерной среды.

Подготовка зависимостей из корня:

```sh
uv sync
```

Команды Django выполняются из `app/`, интерпретатором окружения проекта:

```sh
python manage.py migrate
python manage.py runserver 127.0.0.1:8000
```

Параметры локального запуска описаны в [DEVELOPMENT.md](DEVELOPMENT.md): `DEBUG=True`, `USE_HTTPS=False`, подходящий `ALLOWED_HOSTS` и локальная база. Не перезаписывайте существующий `.env`; для разовой проверки задавайте переменные в окружении процесса.

Для демо используйте отдельную временную SQLite-базу. **`demo_seed` стирает всю выбранную базу.** До запуска проверьте фактический `DATABASE_URL` и включите `DEMO_MODE=True` только в изолированном демо-окружении. Затем выполните из `app/`:

```sh
python manage.py migrate
python manage.py demo_seed
python manage.py runserver 127.0.0.1:8000
```

В [capture_readme.py](capture_readme.py) есть готовый пример временной базы, заполнения демо, локального WSGI-сервера и браузерной проверки. Команда `uv run --with playwright python docs/capture_readme.py` обновляет скриншоты в `docs/images/`; не запускайте её целиком ради проверки отдельного компонента.

## 5. Интерфейс

- **Стиль сайта важнее палитры примера.** Референс задаёт идею и композицию. Используйте CSS-переменные темы и акцента вместо фиксированных цветов с картинки.
- **Общие компоненты.** Для сайта используйте `ui-*` из `app/static_src/css/ui.css`, темы из `style.css` и палитры из `accents.css`. Для админ-панели — её существующие классы и тему.
- **Общие шаблоны.** Повторяющийся компонент выносите в include, чтобы меню, полная страница и предпросмотр не расходились по поведению.
- **Понятные действия.** Связанные кнопки выравнивайте в общий ряд. Ссылки действий отделяйте от сообщения. Для кнопок только с иконкой задавайте доступное название; выбранному ответу — соответствующее состояние.
- **Мобильная версия обязательна.** Проверяйте десктоп и ширины 320, 390 и 430 px, обе темы и влияние выбранного акцента. Смотрите на переносы, наложения, обрезанный текст, горизонтальное переполнение и удобство нажатия.
- **Реальная страница.** Открывайте затронутые страницы и состояния в браузере, делайте снимок и просматривайте его. Отдельный рендер компонента не проверяет положение меню, шапку, прокрутку и взаимодействия на странице.

## 6. Код, данные и безопасность

- Комментарии и docstring — на русском, по правилам [DEVELOPMENT.md](DEVELOPMENT.md): оформление PEP 8 и PEP 257, законченные предложения и тире «—».
- Модели и миграции принадлежат приложениям проекта. Не используйте `app_label` встроенного приложения Django для моделей проекта.
- Исходники статики меняйте в `app/static_src/`; собранный `static/` не является исходным кодом.
- Права и принадлежность объектов проверяйте на сервере. При изменении состояния сохраняйте CSRF-защиту и используйте подходящий метод запроса. Пользовательский текст экранируйте.
- Избегайте отдельного запроса к базе на каждый элемент списка. При изменении балансов, ставок и итогов ивентов сохраняйте транзакционность и защиту от повторной обработки.
- Не выводите `.env`, токены, пароли и личные данные в логи и сообщения. Зашифрованные поля читайте через существующие `get_*()`; метки HKDF не меняйте без плана миграции.
- Не удаляйте базы, пользовательские файлы и Docker-тома ради проверки. Не используйте `docker compose down -v` для обычного перезапуска.
- Интеграции проверяйте поддельными клиентами и тестовыми данными, если задача не требует реального сервиса. Не отправляйте пробные уведомления реальным пользователям без поручения.

## 7. Проверки перед завершением

Из `app/` запускайте проверки, соответствующие изменению:

```sh
python manage.py check
python manage.py test <затронутые_приложения>
```

После изменения моделей:

```sh
python manage.py makemigrations --check --dry-run
```

Общая проверка сайта:

```sh
python manage.py test
```

Для бота из `tsbot/`:

```sh
python -m unittest discover -s tests -t .
```

Настоящий gpg проверяется отдельно по `DEVELOPMENT.md`; при необходимости используйте контейнерную проверку `backups`. Не считайте её выполненной, если тест пропущен или использована подмена.

Перед коммитом просмотрите `git diff`, `git diff --check` и `git status`. Убедитесь, что новые файлы включены, секретов и временных артефактов нет, описание соответствует результату. Расширяйте проверки при новых рисках или сбоях, а не повторяйте весь набор без причины.

## 8. Ветки, коммиты и PR

- Работайте в тематической ветке. Перед переключением проверьте текущую ветку и незакоммиченные изменения. Не переписывайте удалённую историю и не удаляйте ветки без поручения.
- Основная ветка — `master`. Готовьте изменения к review через PR. Прямую отправку в `master`, слияние и выпуск релиза выполняйте по соответствующему поручению.
- Заголовок коммита — на русском с префиксом из истории: `UPDATE:`, `FIX:`, `REDESIGN:` по смыслу. Для содержательных изменений после пустой строки добавляйте список конкретных изменений.
- Не добавляйте фиктивные `Co-Authored-By` и не копируйте подписи других агентов из примеров.
- Описание PR объясняет проблему, итоговое поведение и выполненные проверки. Историю переписки и отложенные подходы включайте только для объяснения важного решения.
- Перед удалением старой ветки по поручению проверьте, что её PR слит. Удаление локальной ветки и ветки на GitHub — разные действия.

Пример сообщения:

```text
UPDATE: уведомления в стиле дашборда

- меню и страница уведомлений используют общую карточку
- ответы на ивенты доступны прямо из уведомления
- действия адаптированы для мобильных экранов
```

## 9. Документация и передача результата

Рабочие планы и отчёты по этапам ведите в чате. Не создавайте для них отдельные файлы в `docs/` или других каталогах репозитория без прямой просьбы пользователя. В документации сохраняйте актуальные инструкции и описание итогового поведения.

При изменении команд, настройки или архитектуры обновляйте `DEVELOPMENT.md`; пользовательские сценарии — в `GUIDE.md`, публичное описание возможностей — в `README.md`. Ссылайтесь на существующие пути и работающие команды. Не добавляйте в общие правила абсолютные пути одной машины.

Версию и теги меняйте в рамках выпуска релиза. Порядок выпуска и серверного обновления описан в `DEVELOPMENT.md`.

В результате задачи кратко сообщите, что изменилось, что проверено, что осталось непроверенным, и состояние коммита или публикации, если они входили в поручение.
